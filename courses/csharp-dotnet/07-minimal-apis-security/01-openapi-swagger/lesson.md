# Module 7, Lesson 01 — OpenAPI & Swagger

Every API you've built so far, someone else has to figure out how to call — what endpoints exist, what they expect, what they return. **OpenAPI** is a standard, machine-readable format describing exactly that; **Swagger UI** is the most common tool for browsing and trying out an API described by it. This is the "Integrated Swagger UI" deliverable from the university plan's Week 5.

## Generating an OpenAPI document

.NET 10 has this built in — no third-party package required for the document itself:

```csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddOpenApi();

var app = builder.Build();
app.MapOpenApi();

app.MapGet("/students", () => new[] { "Ali", "Sara" });

app.Run();
```

| Piece | Meaning |
|---|---|
| `builder.Services.AddOpenApi()` | Registers the machinery that inspects your endpoints (routes, parameters, response types) and builds a description of them. |
| `app.MapOpenApi()` | Exposes that description as JSON at `/openapi/v1.json`. |

Run the app and visit `/openapi/v1.json` — you'll see a JSON document listing every endpoint, its route, and (as much as it can infer) its request/response shapes. Nothing you wrote had to change — this is generated by inspecting your `app.MapGet`/`[HttpGet]` registrations directly.

## Swagger UI — an interactive page for that document

The JSON document alone isn't friendly to read by hand. Swagger UI renders it as a browsable, clickable page where you can see every endpoint and even send test requests directly from the browser. Adding it (via the `Swashbuckle.AspNetCore` package, the most common choice):

```csharp
if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
    app.UseSwaggerUI(options => options.SwaggerEndpoint("/openapi/v1.json", "My API"));
}
```

Visiting `/swagger` in a browser then shows a full interactive page — every route, its parameters, "Try it out" buttons that send real requests. This is almost always wrapped in `if (app.Environment.IsDevelopment())` — you don't want to expose an interactive "try any endpoint" console on a real production server.

## Improving what's generated — summaries and descriptions

Bare route registrations produce a bare OpenAPI document. You can annotate them:

```csharp
app.MapGet("/students/{id:int}", (int id) => Results.Ok())
    .WithName("GetStudentById")
    .WithSummary("Get a single student by their id")
    .Produces<Student>(200)
    .Produces(404);
```

| Piece | Meaning |
|---|---|
| `.WithName(...)` | A unique identifier for the endpoint, usable elsewhere (e.g. `CreatedAtRoute`). |
| `.WithSummary(...)` | Human-readable text shown in Swagger UI. |
| `.Produces<T>(status)` | Documents what shape/status the endpoint returns — helps consumers (and Swagger UI) know what to expect without guessing from your code. |

None of this changes runtime behavior — it only makes the generated documentation richer and more accurate.

## Why this matters

An API without documentation forces every consumer — a frontend developer, another team, a future you — to read the source code to understand it. OpenAPI/Swagger turns "read the code" into "look at a page, click 'Try it out'." It's also the foundation many tools build on: generating client SDKs automatically, API testing tools, and contract testing (Module 9) all consume the same OpenAPI document you're now generating for free.

## Summary
- `builder.Services.AddOpenApi()` + `app.MapOpenApi()` — generates an OpenAPI JSON document from your existing endpoint registrations, no extra work per-endpoint required.
- Swagger UI (`Swashbuckle.AspNetCore`, `app.UseSwaggerUI(...)`) renders that document as an interactive, browsable page — typically restricted to development environments.
- `.WithName()`, `.WithSummary()`, `.Produces<T>()` enrich the generated documentation without changing behavior.
- This documentation is what lets other developers (and tools) understand and consume your API without reading its source code.
